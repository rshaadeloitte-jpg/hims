## Verdict: **CONDITIONAL**

The MIG-010 write path is functionally credible and well-evidenced (legacy parity is documented, L0/L1/L2 coverage exists, count claims verified: **69 backend tests = 60 methods + 11 parameterized invocations; 17 frontend tests = 7 + 7 + 3**). It must **not** be recorded as TESTED until the must-fix list in §3 is resolved. Six findings are security-relevant (two Critical-class, three High), the unit-scope mechanism is not authorization, the audit-hardening patch is uncommitted, and the frontend edit flow is broken for the two unit-scoped entities.

## 1. Executive summary

- **Unit scoping is caller-supplied, not enforced.** Every read/write endpoint takes `unitId` as a client query parameter (`MasterWriteController` 3×, `MasterReadController` 3×) and the use case trusts it (`MasterWriteUseCase.create` uses the param or the payload's `unitId`; `update`/`remove` scope `findByIdScoped` by it). Any authenticated caller can read, create, update or **hard-delete** any unit's records by sending that unit's id. The javadoc claim "unit scope enforced … (authz gap, not replicated)" (IMP-DEC-020) is misleading: enforcement whose scope value is attacker-chosen is a filter, not an authorization control.
- **The read path still has JPQL injection** (`searchFld`/`orderField` raw interpolation and the `searchFld=id` search-term splice in `JpaMasterReadRepository`). This directly contradicts the IMP-DEC-010 record ("search/order/filter fields are whitelisted") and the javadoc in both `MasterReadUseCase` and `JpaMasterReadRepository`. Only `filters` are whitelisted; search and order fields are not.
- **Client-supplied `id` on create is honored** → POST can overwrite an existing row via JPA `merge` (create-as-update) and can inject arbitrary ids into a shared ID space that legacy references depend on. A unit test pins this behavior as "correct".
- **Audit-field forgery:** in the committed slice, `applyLegacyUpdate` copies `addedby/addeddatetime/createdunitid/updatedunitid/synchronizedd` (and `status`) from the payload — update lets clients forge audit provenance; create lets clients set `createdunitid/updatedunitid`. A working-tree patch partially fixes this but is uncommitted and leaves `createdunitid/updatedunitid` copyable, with no tests.
- **DELETE is a hard delete** while legacy (`?__cufl=status`) and the accepted AGT-02 design (D-7/§2.7) define soft-delete — unrecorded deviation that will complicate MIG-005 gateway parity and shadow-mode operation.
- **Frontend:** pagination math, query keys, zod adapter and error parsing check out; the auth header and dev credentials are baked into the bundle with production-unsafe defaults; and the **edit screen cannot load or save unit-scoped entities** (no `unitId` sent on GET-by-id/PUT).
- **Outbox:** same-transaction append is correctly implemented (`@Transactional` REQUIRED propagation); but the "idempotencyKey" contains a random UUID (not idempotent), the table has no unique constraint on it, DLQ rows are parked with no replay job and the configured DLQ topic is never used, and the L2 test proves co-presence, not rollback atomicity.

## 3. Must-fix before the MIG-010 slice is recorded TESTED

1. **F-2** — JPQL injection in the read path: allowlist `searchFld`/`orderField` per entity (persisted-field or registry whitelist), bound-parameter the `searchFld=id` term; add injection regression tests. (If formally out of slice scope, correct the IMP-DEC-010 record and track as P0 — the code contradicts the governance record today.)
2. **F-1** — Unit scope: bind `unitId` to the authenticated principal (or explicitly gate the write endpoints in non-dev deployments until MIG-004); correct IMP-DEC-020 wording ("enforced" → "caller-supplied"); add forged-unitId rejection tests.
3. **F-3** — Client-supplied `id` on create: server-assigned ids only (reject payload id), or a gated legacy-parity opt-in with an existence check (409) so create can never overwrite.
4. **F-4** — Commit the audit-skip patch; extend it to `createdunitid`/`updatedunitid`; add create+update tests proving payload audit fields are ignored.
5. **F-5** — Decide soft vs hard delete; implement soft-delete parity (or record an explicit deviation with the gateway remap) — align with AGT-02 §2.7.
6. **F-6** — Frontend: send `unitId` on getById/PUT so unit-scoped edit works; add a scoped-entity edit test.
7. **F-9** — Deterministic idempotency key (or unambiguous event-id semantics) + uniqueness constraint + consumer dedupe contract.
8. **F-10** — DLQ: publish to the configured DLQ topic or add a replay/alert job; no silent event loss.
9. **F-13a / F-11** — Fix the vacuous null-skip test; add the rollback-atomicity (no outbox row) test.
10. **F-14** — Update-miss → 404 (or explicit gateway remap decision) and regenerate the OpenAPI contract (201 + write error responses).
11. **F-19** — Commit the working-tree change with tests; align TEST-STATUS/IMPLEMENTATION-STATUS claims with the committed tree before TESTED.

**After the must-fix list:** address F-7 (documentation + real-auth-flow test), F-8 (bundle creds gating), F-12 (server validation), then re-run the full suite and re-issue this review before recording TESTED.

## 4. Checklist responses

1. **Write-path security** — Unit-scope "enforcement" is caller-supplied (F-1); no delete/role authorization; BEXA031→400/misleading message (F-14); sequence names are registry-sourced only (safe; F-16 defense-in-depth); mass-assignment: unknown fields are silently dropped by Boot's ObjectMapper (no arbitrary-column write), but known sensitive fields are assignable — id (F-3) and audit fields (F-4). `nextId` is registry-only → no sequence injection.
2. **Dev profile** — `DevSecurityConfig` is `@Profile("dev")` and inert otherwise ✓; permitAll set matches the default chain's ✓ (but not asserted by any test, F-13c); credentials are dev-only defaults (acceptable, F-8 hygiene); audit fields on **create** are over-stamped after mapping (addedby/addeddatetime/synchronizedd safe) but `createdunitid/updatedunitid` payload values persist (F-4).
3. **Outbox** — Append runs in the same DB tx (REQUIRED propagation from `@Transactional` use case) ✓ code-level; test only proves co-presence (F-11); idempotencyKey is a random-UUID misnomer (F-9); DLQ handling half-implemented — no topic publish/replay/alert (F-10).
4. **Frontend** — Client logic is thin (schema adapters + RHF + react-query; no business rules enforced client-side — the gap is server validation, F-12); auth header: dev creds baked in with production-unsafe defaults (F-8); schema adapter tests cover coercion/required/readOnly/select ✓; pagination math verified: `page = pageIndex*pageSize` → server `offset = (page/count)*count = pageIndex*pageSize` exactly ✓ (over-enable only on exact page-size multiples, documented); **edit flow broken for scoped entities** (F-6).
5. **Schema design (AGT-02)** — ONE-TABLE-ONE-OWNER and D-1 single-writer stock are respected and well-argued (item vertical → `ihms_item`; doctor ownership contested but flagged D-2) ✓; sequence/IDENTITY policy consistent with IMP-DEC-003 ✓; parity hazards: hard-delete vs design's soft-delete (F-5), registry cannot model global/unscoped entities (D-6 geo; F-15), dual parity/clean table writes for the gateway are unplanned in MIG-010, and `MasterDataChanged` carries `{op,masterType,masterId}` only — no snapshot for reconciliation.
6. **Tests** — Counts verified (69/17). False-pass/weak spots: vacuous null-skip assertion (F-13a); security tests inject the SecurityContext and cannot detect the absent authN mechanism (F-7/F-13b); same-tx atomicity not really proven (F-11); no adversarial coverage for the security findings; DevBasicAuthTest context differs from production (both chains imported).
7. **Systemic** — Read-path JPQL injection contradicts IMP-DEC-010 (F-2); uncommitted fix + tracker claims ahead of committed tree (F-19); OpenAPI drift (201, missing error responses); no optimistic-locking/versioning on writes (last-write-wins, legacy parity); correlation-id echo hygiene (F-17).
